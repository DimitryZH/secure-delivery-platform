## Architecture and ownership

Use `shop.runtimeplatforms.dev`, with a public Cloud DNS zone at exactly `shop.runtimeplatforms.dev.` delegated from the existing parent. Terraform never manages the parent zone, registrar, portfolio or mail records. The apex A record and Certificate Manager DNS-authorization CNAME live in the child zone. No wildcard or parent certificate is requested.

Choose `gke-l7-global-external-managed`: one Premium global IPv4 NamedAddress, ports 80 and 443, Certificate Manager certificate map, a host-restricted HTTPS HTTPRoute to only `dev/frontend:80`, and a separate HTTP redirect route with no backend. The GKE controller creates/owns forwarding rules, proxies, URL maps, backend service, health check, NEGs and managed firewall integration. Terraform owns only the reserved address, child DNS zone/records, DNS authorization, certificate/map/entry, MODERN TLS_1_2 SSL policy, Armor policy and Gateway API enablement. GCPGatewayPolicy attaches that exact SSL policy; preflight rejects a weaker TLS profile. Cloud Deploy owns six new namespace-scoped objects: Gateway, two HTTPRoutes, GCPBackendPolicy, GCPGatewayPolicy and HealthCheckPolicy. Existing Services stay ClusterIP. No Ingress, direct NodePort/LoadBalancer Service, wildcard route, additional backend or ReferenceGrant is introduced.

The global choice avoids the regional proxy-only subnet and regional certificate attachment path. It supports the selected certificate-map integration and HTTPRoute traffic splitting. Future [Cloud Deploy Gateway canary](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary/gke/gateway-api) needs a separately reviewed `gatewayServiceMesh` strategy, stable/canary Service inventory and capacity; this change does not implement canary. [IAP through GCPBackendPolicy](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-gateway-resources#configure_iap) is a future backend access-policy change with explicit identities and OAuth/secret treatment. A separate Service/backend is needed if public demo and protected access must coexist without one policy overriding the other. No IAP bypass or automatic compatibility claim for future policy combinations is made. Regional access could be reconsidered for an explicit locality/Standard Tier need; global routing does not make this single-zone workload HA.

## Protection and exact deployment contract

The HealthCheckPolicy uses HTTP `/_healthz` on the frontend Pod port 8080. GCPBackendPolicy attaches only `shop-dev-edge` Armor and enables 100% sampled backend request logs using the GKE integer scale (`sampleRate: 1000000`). Never confuse that scale with the Compute API floating-point logConfig scale. Do not log request bodies or publish checkout/session data.

The live Armor Standard policy `shop-dev-edge` has four rules. Priority `100` denies the exact path `/__sdp_edge_probe__` with 403. Priority `1000` enforces the v3.3 sensitivity-1 SQLi/XSS rules. Priority `2000` throttles at 1200 requests per 60 seconds per IP with `deny(429)` on exceed. The default rule allows other traffic.

The Terraform input `shop_edge_enforce_evaluated_rules` defaults to `false` for bootstrap preview. For an enforcement plan in the existing foundation workspace, pass `-var=shop_edge_enforce_evaluated_rules=true` alongside the existing inputs. Keep this value in the reviewed inputs for subsequent plans that should preserve enforcement. The applied enforcement plan changed only `google_compute_security_policy.shop_edge` and its operator output.

`complete.py` now renders 45 exact resources, retaining all accepted application/security/telemetry contracts. The six endpoint resources carry frontend/release/digest/deployment metadata. Inventory rejects changed hosts, classes, listeners, TLS/certificate-map binding, routes/weights/backends, redirects, health checks, Armor policy, unknown metadata and extra/missing resources. Existing generated-label comparisons remain exact and derive expected values from reviewed Cloud Deploy context. No arbitrary labels or metadata are stripped. Actual server render must be inspected before first rollout; offline rendering is not server-render acceptance.

Prepare uses the existing CLI with a new unique Cloud Deploy release and merged deployment SHA. Keep producing SHA unchanged. Source staging, immutable source/inventory annotations, create-only upload, generations and 75-minute retention requirements from [complete procedure](complete-README.md) still apply. The initial rollout must remain disabled.

Preflight adds fresh release/deployment-bound endpoint readbacks, exact project/global address/host/DNS binding, active exact-domain certificate with expiry margin, exact certificate-map entry, and four exact Armor preview rules. Independent image/attestation checks, capacity, Binary Authorization, sample baseline, caller authority and protected artifacts remain mandatory. The `endpoint` section is the explicit schema in `complete.py:endpoint_evidence`; API readbacks must be independently reviewed and normalized only into those documented fields. Keep raw API responses privately. Resolve project ID/number aliases using independent project mapping; do not derive expected identity from labels. Require fresh actual certificate-map entry/listing, child authoritative A/delegation, and actual Armor rule actions/preview/thresholds. The initial endpoint preflight is for the bootstrap preview phase; the later Armor-only enforcement transition needs its reviewed Terraform plan and allowed/denied evidence, not a second application deployment. A future application rollout while Armor is enforced needs a reviewed corresponding preflight phase contract; do not weaken the preview check ad hoc.

The preflight CLI submits the Gateway from the verified rendered inventory to the reviewed dev Kubernetes API with `kubectl apply --server-side=false --dry-run=server`. This matches the client-side apply used by the resolved Skaffold `kubectl` deployer. It uses an isolated kubeconfig with the reviewed cluster endpoint and CA, and authenticates with `gke-gcloud-auth-plugin`. The caller needs a compatible `kubectl` and the auth plugin on PATH, permission to read the cluster, and Gateway read and dry-run apply access. Inventory and artifact checks must pass before admission. Preflight requires a successful dry-run write observed at the dev API and blocks on any Gateway dry-run HTTP 409, including a conflict that kubectl retries. If client-side apply computes no changes, preflight submits a dry-run merge patch pinned to the observed resource version to exercise admission. Snapshot freshness is checked again after admission.

The global HTTPS listener uses port 443 and the `networking.gke.io/certmap` annotation without a listener `tls` block. In the failed `dev-full-001` rollout, Kubernetes rejected the explicit Terminate block because it lacked certificateRefs or options. The corrected form was admitted on the dev API in dry-run using the failed release's rendered Gateway with only that block removed. The corrected renderer produces the same Gateway for that revision and context.

The `dev-full-001` rollout left two HTTPRoutes and three policies. Their last-applied specs and release annotations matched its render, and server dry-run of the corrected endpoint inventory passed over those objects. Rollout `dev-full-002` then succeeded in Cloud Deploy and created the Gateway, but GKE reported `Programmed=False` with `GWCER104` because the HTTPRoute used an explicit `requestRedirect.port`. The reserved IP had no forwarding rules.

The redirect route stays on the HTTP listener and uses `scheme: https`, the reviewed hostname and status 301. The selected GatewayClass supports these fields and uses the HTTPS default port. Preflight rejects an explicit redirect port even if the exact inventory and commitment match. Both route versions passed server-side dry-run against the existing HTTPRoute, while the corrected dry-run result omitted the port and preserved the HTTP listener binding. [GKE GatewayClass capabilities](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/gatewayclass-capabilities) · [GKE HTTP-to-HTTPS example](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways#configure_http-to-https_redirects)

For the corrected release, the operator compared the existing Gateway, two HTTPRoutes and three policies with the prior rollout evidence before reapplying them in place. Foreign resources, spec drift, or a failed dry-run block that recovery. The corrected admission check accepted a changed deployment SHA, rejected the previous invalid HTTPS listener, and left the live Gateway identical before and after the checks. The new protected release passed fresh bootstrap preflight before the authorized rollout.

## Live acceptance on dev-full-003

Release `shop-106-849487e-1a9fbe62` deployed to `catalog-dev → dev` from configuration `849487e988ec8f67700de183ab4b61e5f65d4966`. The server rendered 45 resources and bootstrap preflight passed all 40 checks, including Gateway admission and protected artifact readback. Gateway and HTTPRoutes became ready, the frontend backend reported `HEALTHY`, and the trusted application and Collector digests matched. Binary Authorization remained enforced. Sample-service dev, stage, and prod returned HTTP 200 during rollout verification.

The delegated hostname resolved to `8.233.86.84` through the approved child zone. The parent website and mail DNS records matched their baseline. The managed certificate and certificate map served the exact hostname. HTTPS returned 200 on TLS 1.2 and 1.3, TLS 1.0 and 1.1 were rejected, and HTTP returned 301 to HTTPS with the path and query preserved. The unknown Host test returned 404 from the default backend.

One synthetic checkout under enforcement covered browse, cart, and order confirmation. The scoped Redis cleanup deleted the test session key and verified `EXISTS=0`. The owned port-forward closed after cleanup.

Cloud Armor logged HTTP 403 and `DENY` for the SQLi and XSS probes under rule `1000`. A temporary rule at priority `1500`, scoped to one IP, `GET /_healthz`, and a unique header, returned HTTP 429 on the fourth request of a series at a threshold of 3 requests per 60 seconds. Its log showed `DENY` and `RATE_LIMIT_THRESHOLD_EXCEED`. The temporary rule was removed, the original policy was restored, and the follow-up request returned 200 with a healthy backend.

Direct `429` verification of the live rule `2000` at 1200 requests per 60 seconds per IP remains `NOT_CONFIRMED`. The final bounded series logged all 1220 requests as `RATE_LIMIT_THRESHOLD_CONFORM` under enforcement and returned 200 for each. A search of the available frontend logs in the recorded post-apply window found no enforced `2000` exceed with HTTP 429. The temporary rule proves the throttle deny path at its test threshold.
