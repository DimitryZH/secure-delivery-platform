# Log-based Metrics

The three project-scoped definitions in [logging-metrics.tf.json](../../terraform/foundation/logging-metrics.tf.json) use native Terraform JSON syntax so their filters, descriptors, extractors, and histogram boundaries can be tested offline with the standard library. They reuse the foundation Google provider, project, cluster name, and enabled APIs. No additional identity, collector, backend, or application instrumentation is introduced. The metrics are deployed through the reviewed Terraform path. Dev request and latency ingestion and `health_check=true` classification were observed. The error metric existed without series because no matching 4xx/5xx logs occurred in the observation window; this is not proof of zero future errors. No artificial failures were generated. Both classifications are supported by the definitions, but `health_check=false` was not observed in the live sample window.

| Logging metric name | Monitoring type | Kind / value / unit | Signal |
| --- | --- | --- | --- |
| `sample_service_requests` | `logging.googleapis.com/user/sample_service_requests` | DELTA / INT64 / 1 | All matching HTTP responses |
| `sample_service_errors` | `logging.googleapis.com/user/sample_service_errors` | DELTA / INT64 / 1 | HTTP 4xx and 5xx responses |
| `sample_service_latency_ms` | `logging.googleapis.com/user/sample_service_latency_ms` | DELTA / DISTRIBUTION / ms | Server-side request handling duration |

The common filter requires `k8s_container`, the configured cluster, container `sample-service`, stdout, `event=http_request`, `service=sample-service`, HTTP status in [100, 600), and explicit health classification. Each allowed namespace must match the payload environment: dev, stage, or prod. Startup, other services/clusters, missing classification, and conflicting environment records are excluded. Errors additionally require status >= 400; latency requires a non-negative `latency_ms` and extracts `EXTRACT(jsonPayload.latency_ms)`. Failed/missing distribution extraction produces no latency sample; compare distribution counts with request counts. Status is authoritative for the error counter; do not filter `jsonPayload.severity`, because GKE extracts severity to LogEntry.

Only two user-defined labels are added: `environment` (STRING, three values) and `health_check` (BOOL, two values), extracted from the matching JSON fields. Service is fixed by the filter. No path, method, status, Pod, release, build, commit, digest, or trust-reference label is added. This bounds custom combinations to six per monitored resource, not six total time series: built-in `k8s_container` resource labels still include Pod/container identity and rollouts create new resource series. Aggregate across Pods for environment totals; aggregation does not reduce ingestion cardinality or cost. Review actual active-series volume before later expansion. See [label cardinality](https://docs.cloud.google.com/logging/docs/logs-based-metrics/labels).

Both health and non-health traffic are collected. Select `health_check=false` for application traffic, true for health probes, or omit that filter intentionally. Error count includes client errors and server errors; it does not count requests that never reach the application or an idle connection without a response. A query-string GET to the health path is classified false by the existing routing contract.

Latency bounds are 1, 5, 10, 25, 50, 100, 250, 500, 1000, 2500, and 5000 ms. The first bucket covers [0, 1), intermediate buckets are lower-inclusive/upper-exclusive, and overflow covers >= 5000 ms. These emphasize the small service's sub-millisecond handling while retaining slower responses; they are histogram resolution, not performance targets or an SLO. Latency is server-side handling duration, not client-observed latency. Merge aligned distributions before estimating percentiles; do not average per-Pod percentiles.

Log-based metrics are forward-looking, sampled/delayed operational evidence, not a backfill of historical acceptance logs. Missing time series are not proof of zero traffic/errors or healthy availability. No artificial error traffic is generated for repository validation. Definitions alone do not prove extraction, ingestion, IAM suitability for apply, or billing impact. Existing platform resource labels and Logging extraction behavior remain subject to read-only review as the workload changes.

Availability reuses existing GKE deployment-state available/desired replicas; no custom availability metric or monitoring configuration change is needed. See [Observability](../../docs/observability.md#release-health-metrics) and the [read-only inspection procedure](../../docs/operator-runbook.md#release-health-metric-inspection). Metrics do not establish provenance, verification, attestation, admission, or automatic promotion/rollback authorization.
